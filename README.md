# GIS MT True API — внутренняя проверка кодов маркировки «Честный Знак»

Внутреннее web-приложение для склада: проверка кодов маркировки (КМ) через
True API ГИС МТ. Основной сценарий — Android-ТСД с аппаратным DataMatrix-сканером
под Fully Kiosk Browser (сканер в режиме `output to cursor`).

Назначение:

- сканирование КМ и проверка фактического состояния через True API;
- понятный «складской» вердикт по каждому коду (OK / внимание / ошибка);
- пакетная проверка списка КМ;
- баланс по GTIN;
- работа нескольких юридических лиц, каждое со своим bearer-токеном.

Приложение сознательно простое: FastAPI + vanilla JS, без внешней БД,
очередей и микросервисов.

---

## Возможности

### Одиночный скан

Один DataMatrix (КМ), запрос свежих данных True API. Результаты проверки
**не кэшируются** — каждый скан даёт актуальный ответ ЧЗ.

Карточка результата показывает:

- `productName`;
- `quantityInPack`;
- status (с русским маппингом);
- owner (наш / чужой);
- GTIN и Serial (в раскрываемых технических данных).

### Business policy (verdict)

Интерпретация фактического статуса ЧЗ для сотрудника склада. Реализована
на backend в `models.py` (`business_verdict`) — явный whitelist, без принципа
«нет `error_category` => OK». Исходные настройки (меняются в админке):

| True API status | verdict | UI      |
| --------------- | ------- | ------- |
| `APPLIED`       | ok      | зелёный |
| `INTRODUCED`    | ok      | зелёный |
| `EMITTED`       | warning | жёлтый  |
| неизвестный     | warning | жёлтый  |
| ошибка DM/API/КМ| error   | красный |

По умолчанию `EMITTED` = код эмитирован, но нанесение ещё не зарегистрировано. Это НЕ
красная ошибка и НЕ зелёный успех — для склада это жёлтое предупреждение:
если код физически уже нанесён на товар, следует проверить отчёт о нанесении.

Неизвестный (новый) статус True API по умолчанию **не** считается зелёным —
отображается как warning, без придумывания бизнес-смысла.

Разделение ответственности:

- `TrueApiClient` возвращает факты (сырой статус ЧЗ);
- `Service` / business policy определяет verdict;
- frontend только отображает готовый verdict.

### quantityInPack

`quantityInPack` — количество единиц товара, зашитое в конкретный КМ при
отчёте о нанесении. Это **не** количество кодов и **не** balance quantity.

В UI одно из главных полей, порядок:
`productName -> quantityInPack -> status -> owner`.

### Пакетная проверка (batch)

Несколько КМ (до 1000 на запрос). Сводка по результату: Total, OK, Warning,
Error. По каждой строке — свой verdict и `quantityInPack`, раскрываемые
технические данные.

### Баланс

Баланс по GTIN и статусам `EMITTED` / `APPLIED` / `INTRODUCED`. Каждый статус
считается независимо. Разделяются два показателя:

- `km_count` — количество КМ;
- `quantity_sum` — сумма `quantityInPack` по КМ (заполняется для `APPLIED` и
  `INTRODUCED`; для `EMITTED` поле не заполняется).

Итоги считаются только по организациям **с токеном**; организации без токена
перечисляются на уровне организации, но не тянут вниз общий итог.

### Несколько организаций

Справочник организаций (`organizations.py` + конфиг `ORGANIZATIONS`) и
отдельный bearer-токен на каждую (`tokens.py`). Выбор организации для запроса
через `org_inn` или автоматически — первая организация с настроенным токеном.

## Kiosk / ТСД UX

Приложение рассчитано на Android-ТСД. Сканер работает в режиме
`output to cursor` (аппаратный сканер печатает символы в текущий focus).

### Scan focus lock

Пока открыта вкладка «Скан», поле сканирования автоматически держит focus —
сотруднику не нужно вручную тапать по input перед каждым КМ:

- focus восстанавливается после `blur`, клика/tap, возврата приложения
  (`window focus`, `pageshow`, `visibilitychange`);
- глобальный keyboard-wedge fallback ловит скан, если WebView всё же потерял
  focus (printable-символы идут в поле, `Enter` запускает проверку);
- восстановление event-driven, без агрессивного polling;
- вкладки Batch и Balance **не** перехватываются, ввод не воруется из
  `INPUT`/`TEXTAREA`/contenteditable.

Атрибут `inputmode="none"` используется, чтобы не поднимать Android soft
keyboard при автоматическом фокусе.

## Verdict policy

Таблица — см. раздел «Business policy (verdict)» выше.

Ключевой принцип: `EMITTED` и неизвестные статусы **не** меняют глобальное
состояние True API. Если True API успешно ответил — верхняя системная панель
остаётся зелёной («СИСТЕМА РАБОТАЕТ»); жёлтым становится только результат
конкретного КМ.

## True API health / status bar

Status bar отслеживает состояние системы и True API без дополнительных
запросов к ЧЗ: состояние обновляется по итогу каждого scan/batch/balance.

Показывается:

- backend online/offline;
- режим mock/live;
- состояние True API (`unknown` / `ok` / `error`);
- `last_success` и реальная категория последней ошибки;
- список организаций с признаком `token_configured`;
- возраст токена (`token_updated_at`).

### Token age

`token_updated_at` — когда токен был обновлён **нашим приложением**.
Это НЕ точный `expires_at`. Эвристика для отображения:

- до 8 часов — информационно;
- 8–10 часов — «скоро может потребоваться обновление»;
- более 10 часов — «проверьте доступ к ЧЗ».

Фактический `token_invalid`/`unauthorized` от True API имеет приоритет над
этой эвристикой.

## Автоматическое обновление kiosk

`/api/status` отдаёт `build_id`. Frontend опрашивает статус примерно раз в
6 секунд.

`build_id`:

- основной источник — Git short SHA текущего HEAD;
- fallback (без `.git`) — short hash исходников приложения (`*.py`, `*.js`,
  `*.css`, `*.html`).

Если `build_id` изменился:

- ставится pending reload;
- активный scan/batch/balance **не** прерывается;
- reload выполняется после завершения операции (повторный скан автоматически
  не запускается).

Cache busting — `app.js?v=<build_id>` и `style.css?v=<build_id>`. Это важно
для Fully Kiosk, который может держать страницу открытой сутками: при
обновлении приложения ТСД подхватывает свежий frontend без ручного reload.

## Архитектура

Проект сознательно простой: FastAPI, Uvicorn, httpx, Pydantic, Jinja2,
vanilla JS/CSS, файловое хранилище токенов. Без React, Redis, Celery,
микросервисов и внешней БД.

```text
ТСД / Browser
     |
     v
FastAPI (main.py)
     |
     v
Service / business policy (service.py, models.py)
     |
     v
TrueApiClient (trueapi.py)
     |
     v
ГИС МТ True API
```

`TokenStore` (`tokens.py`) — bearer-токены по организациям (файловое
хранилище, заменяемое через `TokenStore` Protocol).

## Token workflow

Обновление bearer-токена организации — через служебную страницу `/admin/token`
(ссылки на неё в основном интерфейсе нет; UUID-токен живёт ~10 часов по данным ГИС МТ).

Auth-flow (по актуальной документации ЦРПТ «Описание True API»):

```
GET /auth/key
   ↓
uuid + data
   ↓
подпись data через УКЭП (КриптоПро CSP)
   ↓
POST /auth/simpleSignIn  ({ uuid, data, unitedToken: true })
   ↓
uuidToken
   ↓
Authorization: Bearer <uuidToken>
```

Порядок:

1. На Windows-машине с КриптоПро CSP и действующей УКЭП запустить
   `refresh_trueapi_token.ps1` — либо двойным кликом по удобному лаунчеру
   `Обновить токен ЧЗ.cmd` (лежит в той же директории и вызывает PowerShell-скрипт):

   ```powershell
   .\refresh_trueapi_token.ps1
   ```

2. Скрипт автоматически ищет доступные сейчас контейнеры закрытых ключей
   КриптоПро (`csptest -keyset -enum_cont -verifycontext -fqcn`), сопоставляет
   их с действующими сертификатами УКЭП в личном хранилище и показывает
   пользователю список. Вы выбираете нужную ЭЦП, скрипт получает challenge
   (`GET /auth/key`) и подписывает `data` УКЭП через `csptest.exe` — подпись
   выполняется по отпечатку (thumbprint), а не по ФИО. На выходе печатаются
   `UUID` + `SIGNATURE`.
3. Открыть `/admin`, войти и выбрать организацию в разделе «Токен».
4. Вставить `UUID` в первое поле, `SIGNATURE` — во второе, нажать «Обновить токен».
5. Backend обменивает `UUID` + `SIGNATURE` на единый токен аутентификации в формате
   UUID (`POST /auth/simpleSignIn` с `unitedToken: true`) и начинает использовать его
   как `Authorization: Bearer <uuidToken>` без перезапуска. ИНН выбранной организации
   (`inn`) передаётся в `/auth/simpleSignIn` вместе с UUID-flow — ЦРПТ требует ИНН
   для реальной авторизации по полномочиям пользователя/сертификата в ГИС МТ.

Bearer-токен хранится **только** на backend; frontend его не получает.
Пара `UUID` + `SIGNATURE` одноразовая и живёт считанные минуты — вставлять
свежий вывод скрипта сразу после запуска. Вручную редактировать
`$certName` больше не нужно: скрипт сам находит доступные контейнеры
КриптоПро и определяет сертификаты, а подпись выполняет по thumbprint.
Реальные auth-данные в репозиторий не попадают.

## Формат TokenStore

`data/tokens.json` — runtime secret, в `.gitignore`, не коммитится.

Поддерживаются два формата (оба читаются, запись всегда в новом):

Legacy:

```json
{
  "7700000000": "TOKEN"
}
```

Новый (с метаданными):

```json
{
  "7700000000": {
    "token": "...",
    "updated_at": "2026-09-11T05:30:00Z"
  }
}
```

Старые записи читаются как есть (`updated_at = null`). При следующем
обновлении токена запись мигрирует в новый формат. Права файла — `0600`.

## API endpoints

- `GET /` — интерфейс проверки КМ (рендер `templates/index.html`).
- `GET /api/status` — состояние backend, True API, организаций, `build_id`.
- `POST /api/scan` — проверка одного КМ.
- `POST /api/scan_batch` — проверка списка КМ (до 1000).
- `POST /api/balance` — баланс по GTIN (статусы EMITTED/APPLIED/INTRODUCED).
- `GET /admin` — общая админка с единым входом.
- `GET /admin/token` — перенаправление в раздел «Токен» общей админки.
- `POST /admin/token` — обмен UUID+SIGNATURE на bearer-токен (защищён).

## Mock-режим

Детерминированный mock без доступа к ЧЗ (`GIS_MODE=mock`). GTIN
`04640638345218` считается «нашим».

Маркеры в serial:

- `Q<число>` → `quantityInPack = <число>` (например `Q500` → 500);
- `EMITTED` → статус `EMITTED`;
- `INTRODUCED` → статус `INTRODUCED`;
- `NOTFOUND` → «КМ не найден»;
- иначе → статус `APPLIED`, quantity `400`.

Чужой GTIN → «чужой» КМ.

## Security notes

- bearer-токены хранятся только на backend, frontend их не получает и не
  логирует;
- `data/tokens.json` в `.gitignore`, права файла `0600`;
- `/admin/*` защищён `ADMIN_KEY` (`hmac.compare_digest`, fail-closed);
- не логировать token / signature / ADMIN_KEY;
- приватные ключи УКЭП на сервере не хранятся (КриптоПро остаётся на Windows-ПК);
- в production — HTTPS через reverse proxy (Caddy/nginx), не выставлять Uvicorn
  голым портом.

## Складские документы: отгрузка и приёмка

В приложении три режима: существующая **сверка КМ**, **отгрузка** и **приёмка**.
Сверка, баланс и их политика статусов сохранены. Складские операции доступны
по `/warehouse?kind=shipment` и `/warehouse?kind=receipt` с ПК и Android-ТСД.
Общая админка: `/admin`, разделы «Токен», «Приёмка», «Отгрузка».

### Обновление и запуск

1. Установите зависимости: `pip install -r requirements-lock.txt`.
2. Настройте `ADMIN_KEY` (не оставляйте демонстрационное значение), `ORGANIZATIONS`
   и токены True API, как описано выше.
3. При необходимости задайте новые переменные:

   | Переменная | По умолчанию | Назначение |
   |---|---|---|
   | `WAREHOUSE_DB` | `data/warehouse.sqlite3` рядом с исходниками | Путь к общей SQLite-базе |
   | `RECEIPT_DEFAULT_ORG` | пусто | ИНН нашей организации для шаблона и формы приёмки |

4. Запустите приложение обычной командой `uvicorn main:app --host 0.0.0.0 --port 8000`.
   Таблицы создаются автоматически. Каталог базы должен быть доступен сервису на запись
   и сохраняться между обновлениями. Для контейнера подключите постоянный том.
5. После обновления перезапустите backend. Существующий `build_id` обновит frontend
   на ТСД, когда закончится отправка сканов и не останется незавершённого ввода.

База рассчитана на один сервер (в том числе несколько процессов uvicorn), с локальным
диском и общей SQLite. Не размещайте её на сетевой файловой системе и не используйте
разные копии базы для разных процессов приложения.

**Единый вход:** откройте `/admin` и введите `ADMIN_KEY`. Сервер создаёт подписанную
сессию на 8 часов в HttpOnly/SameSite=Strict cookie. Сессия общая для трёх разделов,
сохраняется после перезагрузки страницы и завершается кнопкой «Выйти».
Сам ключ не сохраняется в LocalStorage/SessionStorage и не включается в HTML.
При смене `ADMIN_KEY` прежние сессии перестают действовать. По HTTP внутри локальной
сети cookie работает; по HTTPS устанавливается также Secure.
Старые адреса `/admin/token` и `/admin/warehouse` перенаправляют в соответствующий
раздел общей админки, не перенося `?key=...`. Ключ через URL и form-поле `key` не принимается.
Для программного доступа сохранён заголовок `X-Admin-Key`. Для постоянной работы используйте HTTPS и существующие
сетевые ограничения доступа к внутреннему приложению. У складских сотрудников отдельный
интерфейс без административных настроек; индивидуальных аккаунтов сотрудников нет.

### Формат Excel

Скачайте шаблон нужного процесса в административном интерфейсе. Импорт принимает `.xlsx`
до 10 МБ и 50 000 строк; распакованный файл ограничен 80 МБ. Маппинг столбцов не нужен.
Числовые GTIN/ИНН и формулы в исходных данных отклоняются: используйте текстовый формат,
чтобы ведущие нули не терялись.

**Лист «Документ»:** столбцы `Поле`, `Значение`.

| Поле | Отгрузка | Приёмка |
|---|---|---|
| Номер документа | Обязательно | Обязательно |
| Дата документа | ГГГГ-ММ-ДД либо дата Excel | ГГГГ-ММ-ДД либо дата Excel |
| ИНН организации | Наша организация-отправитель | Наша организация-получатель |
| Получатель | Наименование контрагента | Не требуется |
| ИНН получателя | 10 или 12 цифр как текст | Не требуется |

Организацию можно явно выбрать в форме импорта из существующего справочника.
Для приёмки отправитель/поставщик не нужен.

**Лист «Товары», отгрузка:** `PN`, `GTIN`, `Количество`.
Повторяющиеся GTIN объединяются суммированием количества; разные PN для одного GTIN —
ошибка импорта с номером строки. Количество — положительное целое число.

Если PN отсутствует, backend запрашивает `POST /api/v4/true-api/product/info`
с телом `{"gtins": [...]}` и берёт поле `results[].model` — «Модель / артикул производителя».
Лимит запроса — 1000 GTIN, используется имеющийся HTTP-клиент и токены организаций.
Источник: [официальное описание True API](https://docs.crpt.ru/gismt/True_API/).
`name` и `productName` не используются как PN. Отсутствие модели/доступа не отменяет импорт:
показывается предупреждение, PN можно заполнить вручную. Проверка отгрузки также пытается
дозаполнить отсутствующие PN; обычное сканирование не делает таких запросов.

**Лист «Товары», приёмка:** `PN`, `GTIN`, `Код маркировки`, `Количество в КМ`.
Одна строка — один конкретный ожидаемый КМ. GTIN должен совпадать с GTIN в коде;
повтор идентификатора КМ отклоняется. PN допустимо оставить пустым.

### Работа администратора

1. Откройте `/admin`, введите `ADMIN_KEY` один раз на 8 часов.
2. Выберите «Отгрузка» или «Приёмка», скачайте и заполните шаблон, загрузите файл.
3. Откройте карточку: проверьте организацию, реквизиты, позиции и PN.
4. Для отгрузки выберите режим принадлежности. По умолчанию требуется именно
   организация-отправитель; при выключении допускаются только организации нашего справочника.
5. Нажмите «Начать операцию». До запуска документ скрыт от склада.
6. Следите за общим списком сканов и результатом последней проверки. Админский экран
   синхронизируется с той же базой каждые 2 секунды.
7. После завершения отгрузки заполните все PN и нажмите «Скачать файл КМ».
   Файл `Отгрузка_<номер>_КМ.xlsx` содержит `PN`, `GTIN`, `Код маркировки`, по одному
   полному исходному DataMatrix на строку. Автоматической отправки в ЭДО нет.

PN можно исправить перед выгрузкой и после завершения; это не меняет состав товара.
Плановые количества незавершённой отгрузки можно исправить в карточке. Изменение плана
или режима владельца делает результат проверки неактуальным. Приёмка сверяется с
исходным перечнем ожидаемых КМ, который после импорта не редактируется.
Для изменения состава завершённого документа предусмотрена отдельная кнопка
«Возобновить операцию», после неё нужна новая проверка. Прежние выгрузки при этом
автоматически не отзываются.

В разделе **«Токен»** выберите организацию, вставьте UUID и SIGNATURE из существующего
Windows-скрипта и нажмите «Обновить токен». Повторно вводить административный ключ
при переходе между разделами не нужно. Рядом с организацией видны наличие токена и
время последнего обновления.

В карточке документа есть **«Удалить документ»** для любого статуса, в том числе
завершённого. В диалоге нужно ввести его номер и подтвердить удаление. После этого
документ исчезает из списков администратора и склада; открытые складские экраны
блокируют дальнейшую работу при ближайшей синхронизации. Сервер сразу запрещает
новые сканы, проверку, завершение, редактирование и экспорт удалённого документа.
Удаление логическое: `deleted_at` фиксирует время, исходные позиции, КМ и история
проверок сохраняются в базе. Для восстановления откройте фильтр «Раздел → Корзина», выберите документ и нажмите
«Восстановить из корзины». Реквизиты, позиции, КМ и исходный статус сохраняются.
Для активного документа после восстановления нужна новая проверка; завершённый
возвращается с сохранённым итоговым составом и результатом. В корзине редактирование,
сканирование, запуск и экспорт недоступны.
Если во время подтверждения другой сотрудник изменил документ, удаление возвращает
409 и требует обновить карточку и подтвердить ещё раз. Во время выполняющейся
проверки удалить документ нельзя: нужно дождаться её завершения.

### Работа склада и продолжение с другого устройства

Рабочий экран склада начинает со сканирования: номер документа, организация,
счётчик КМ, поле ввода и кнопка «Проверить». На экране ТСД 320×568 поле и проверка
видны без прокрутки. Результат проверки, состав, список КМ и реквизиты находятся
ниже в раскрываемых блоках. Ошибки раскрываются автоматически; из результата можно
сразу открыть список ошибочных КМ. Кнопка завершения появляется после совпадения.
В таблице PN закреплён слева при горизонтальной прокрутке. Светлая и тёмная темы
используют контрастные подписи, границы и цвета статусов.

1. Откройте режим отгрузки или приёмки, выберите запущенный документ.
   В списке склада видны только документы в работе. Завершённые документы остаются
   в админке; после возобновления администратором они снова появляются у склада.
2. Сканируйте аппаратным DataMatrix-сканером на ТСД, USB-сканером на ПК либо вводите код
   вручную с Enter/кнопкой «Добавить КМ». Используется общий механизм удержания фокуса
   со страницей одиночной сверки. Сканер должен передавать полный код и разделители GS.
3. Каждый уникальный скан сохраняется на сервере сразу. **Запросов к ГИС МТ и пересчёта
   фактической таблицы при сканировании нет.** Меняются только общий список и счётчик КМ.
4. При повторе видны КМ и время первого скана. «ОК, продолжить» сохраняет исходный КМ.
   «Удалить код из документа» удаляет сохранённый КМ, чтобы изъять его без поиска в списке.
   После выбора можно продолжать сканирование; удаление требует повторной проверки.
5. Нажмите **«Проверить»**. Только это действие обновляет фактические количества.
6. Если приёмка ещё не заполнена, продолжайте сканирование: это жёлтое предупреждение.
   Исправьте ошибки в считанных КМ и повторите проверку.
   После успешной проверки появится диалог: «Завершить сборку/приёмку» либо
   «Продолжить работу». Завершение подтверждается отдельно, затем открывается список
   оставшихся документов. Если другой сотрудник изменил состав, требуется новая проверка.

Другой сотрудник может открыть тот же документ на ПК или ТСД и сразу продолжить работу.
Ничего переносить не нужно. Сканирования разных устройств не перезаписывают друг друга;
счётчики, список и статус синхронизируются без перезагрузки каждые 2 секунды. Это локальные
запросы к backend, а не к ГИС МТ. Дубликаты блокируются общей уникальностью SQLite
`(document_id, cis)` внутри транзакции.

При потере соединения неподтверждённый ввод остаётся в очереди страницы и в sessionStorage
этого браузера. Интерфейс показывает число несохранённых КМ и кнопки повторной отправки
или удаления ошибочного ввода. Это страховка от сбоя, а не основное хранилище:
на другом устройстве видны только подтверждённые сервером сканы. До ухода с устройства
дождитесь пустой очереди. При полной очистке данных браузера неотправленный ввод не сохранится.

### Правила проверки

**Отгрузка:** используется существующий `Service.scan_batch` и ограничение `cises/info`
по 1000 КИ на запрос. По умолчанию для каждого КМ обязательны статус **`INTRODUCED`**, достоверное
положительное целое `quantityInPack`, подходящий `ownerInn`, GTIN из документа и полный
криптохвост для последующей выгрузки. Набор допустимых статусов меняется в админке.
При исходных настройках `APPLIED`, `EMITTED`, неизвестные статусы, отсутствие
владельца/количества и ошибки API блокируют завершение. Неизвестного владельца backend
пробует получить с доступными токенами других наших организаций. Общая политика
`business_verdict` не изменена. Собранное количество — сумма количества внутри допустимых
КМ, а не число сканов. Недобор, перебор и лишний GTIN блокируют завершение.

**Приёмка:** локальное сравнение точного набора полных КМ из Excel. Запросы в ГИС МТ
не выполняются. Одного совпадения количества недостаточно. Учитываются AIM-префиксы
сканеров и явные замены GS (`{GS}`, `^]`), при этом отличающиеся криптохвосты не совпадают.
Неоднозначный код с серийным номером длиннее GS1-лимита отклоняется, вместо угадывания
границы серийного номера нужно настроить передачу GS на сканере.

Если сканер напечатал КМ с кириллицей из-за русской раскладки Windows, приложение
восстанавливает английские символы по клавишам с учётом регистра и знаков препинания.
Это работает в одиночной/пакетной сверке и складских операциях. Сканы, уже набранные
латиницей, не меняются. На складе исправленный полный КМ сохраняется и выгружается
латиницей, чтобы ошибочная раскладка не попадала в итоговый файл.

Полный исходный код, канонический полный код и идентификатор для сравнения хранятся
раздельно. В выгрузку идёт исходный полный код, **не** `normalized_cis`/`api_cis`.
Excel-коды записываются как строки; управляющие символы кодируются стандартным OOXML
`_xNNNN_`. Чтение различает управляющий GS и буквальный текст `_x001D_` внутри крипточасти.
Не копируйте коды через редакторы, удаляющие управляющие символы.

Проверка фиксирует снимок состава и его версию. Пока идёт запрос, другие устройства
могут сканировать. Результат сохраняется именно для проверенной версии: при изменениях
показываются «Данные предыдущей проверки», завершение блокируется. Изменение плана и
режима принадлежности также меняет версию. Повторные проверки одного документа
одновременно не запускаются. Аварийно прерванная проверка освобождается по таймауту
аренды через 10 минут; собственная длительность проверки ограничена 9 минутами.
Завершение проверяет все условия атомарно на backend и не делает скрытых запросов к ГИС МТ.

### Новые API

| Доступ | Метод и путь | Действие |
|---|---|---|
| Склад | `GET /api/warehouse/documents?kind=shipment` | Запущенные/завершённые документы |
| Склад | `GET /api/warehouse/documents/{id}` | Общий состав, план и последняя проверка |
| Склад | `POST /api/warehouse/documents/{id}/scans` | Добавить `{"code":"полный КМ"}`, ответ содержит `duplicate` |
| Склад | `DELETE /api/warehouse/documents/{id}/scans/{scan_id}` | Удалить исходную запись КМ |
| Склад | `POST /api/warehouse/documents/{id}/check` | Явная проверка документа |
| Склад | `POST /api/warehouse/documents/{id}/complete` | Атомарное завершение по актуальному результату |
| Админ | `GET /api/admin/warehouse/settings` | Справочник, текущие настройки, схема и история |
| Админ | `GET /api/admin/warehouse/templates/{kind}` | Стандартный XLSX-шаблон |
| Админ | `GET/POST /api/admin/warehouse/documents` | Список / импорт multipart: `kind`, `org_inn`, `file` |
| Админ | `GET/PATCH /api/admin/warehouse/documents/{id}` | Просмотр / изменение PN, плана и режима |
| Админ | `DELETE /api/admin/warehouse/documents/{id}` | Удалить документ из работы, сохранив историю; тело `version`, `revision` |
| Админ | `POST /api/admin/warehouse/documents/{id}/start` | Запуск |
| Админ | `POST /api/admin/warehouse/documents/{id}/reopen` | Возобновление завершённого документа |
| Админ | `GET /api/admin/warehouse/documents/{id}/export` | Полные КМ завершённой отгрузки |

Админские API требуют действующую сессию или `X-Admin-Key`. При записи с cookie
обязателен заголовок `X-Admin-Request: 1` (защита от запросов чужого сайта); frontend
добавляет его автоматически. Без административного доступа удаление недоступно.
`POST /api/admin/session` принимает JSON `{"key":"..."}` и выдаёт cookie;
`GET /api/admin/session` проверяет вход; `DELETE /api/admin/session` завершает сессию.
PATCH передаёт полученные из GET
`version`, `revision` и изменённые поля: `pns` (`GTIN → PN`), `quantities` (`GTIN → целое
количество`), `strict_owner` (boolean). Конкурирующее изменение возвращает HTTP 409.
Ошибки импорта содержат лист и номер строки. Значения `kind`: `shipment`, `receipt`.

### Хранение и резервное копирование

Таблицы SQLite: `warehouse_documents`, `warehouse_lines`, `warehouse_expected`,
`warehouse_scans`, `warehouse_checks`. Сохраняются реквизиты, PN с источником, полный
DataMatrix, ожидаемые КМ, сканы со временем, результаты проверок по версиям и даты статусов.
В них нет токенов или административных ключей. Токены по-прежнему в отдельном `TOKENS_FILE`.
База не добавляется в git. Перезапуск приложения не удаляет документы или результаты.

Для согласованной копии работающей базы используйте SQLite backup API:

```python
import sqlite3
with sqlite3.connect("data/warehouse.sqlite3") as source:
    with sqlite3.connect("warehouse-backup.sqlite3") as destination:
        source.backup(destination)
```

Сохраняйте резервную копию вне каталога обновляемого приложения. Альтернатива:
остановите backend, затем скопируйте базу вместе с существующими файлами `-wal`/`-shm`.
Для восстановления остановите сервис, восстановите базу из согласованной копии,
уберите оставшиеся от старой базы `-wal`/`-shm`, проверьте права и запустите приложение.
Отдельно сохраняйте конфигурацию и токены с ограниченными правами доступа.

### Проверка без реальной ГИС МТ

`GIS_MODE=mock` сохраняется. Запуск тестов: `python -m pytest -q`.
Для успешной mock-отгрузки используется GTIN `04640638345218`, организация `0000000001`,
серийный номер с `INTRODUCED` и `Q100` для количества 100, например полный код:
`01` + GTIN + `21INTRODUCEDQ100` + GS + `91EE12` + GS + `92ABCD`.
Организация должна присутствовать в справочнике, для неё нужен mock-токен в текущем
токен-хранилище. Настоящие ключи для mock-режима не нужны. PN берётся из mock-поля `model`.

Автотесты покрывают импорт, PN и его отсутствие, точность Excel/GS/криптохвоста,
политики владельца и статусов, API-сбои, совпадение количества и точного набора КМ,
параллельные сканы, передачу работы между устройствами, устаревшие результаты,
завершение и перезапуск. Аппаратный ввод Fully Kiosk и live-доступ к ГИС МТ нужно
дополнительно проверить на рабочем ТСД с реальными кодами и токенами.

Дополнительный браузерный smoke-тест (Chromium, два независимых клиента, мобильный экран):

```bash
pip install playwright==1.55.0
python -m playwright install chromium
python tests/browser_warehouse.py
```

Он запускает временный mock-сервер с отдельной базой и тестовыми токенами, проверяет
единый вход, сохранение сессии и выход, обновление токена, удаление документа,
админский импорт/PN/запуск/экспорт, синхронизацию ПК и мобильного клиента, дубли,
устаревший результат, завершение, приёмку после перезагрузки и прежнюю одиночную сверку.
Playwright не является зависимостью рабочего приложения.


### Фильтры и разбор расхождений

На складе в списке документов доступны фильтры по нашей организации и наличию сканов:
«Ещё не начато» (0 сохранённых КМ), «Есть сканы» (хотя бы 1 сохранённый КМ).
Это отдельный признак, не статус запуска операции: запущенная администратором
отгрузка без сканов остаётся в фильтре «Ещё не начато».

В админке дополнительно доступны поиск по номеру/контрагенту/ИНН, период дат документа,
статус операции, обращения склада («Проблемные», «Разобраны», «Без обращений»),
а также переключение обычного списка и корзины. Тип документа выбирается вкладкой.
Поиск поддерживает русский регистр. Фильтры комбинируются и сохраняются в текущем
браузере отдельно для отгрузок и приёмок; «Сбросить фильтры» возвращает полный список.
Складские API не открывают черновики и корзину независимо от параметров запроса.

После актуальной проверки с расхождениями у склада появляется небольшая кнопка
**«Сообщить ответственному»**. Можно добавить комментарий. Система сохраняет снимок
результата, план, точные КМ и их ошибки в момент обращения. Это внутреннее обращение
в админке: отправки писем или сообщений во внешние сервисы нет.
Повторная отправка того же открытого обращения с разных устройств не создаёт дубли.
После изменения состава или новой проверки нельзя отправить старый результат.

В админке документ с открытым обращением выделен и находится выше обычных документов.
Кнопка **«Разобрать обращения»** открывает сохранённые расхождения, коды и действия
по документу: запуск, добавление/удаление КМ, изменение реквизитов, проверки,
завершение, удаление/восстановление и разбор обращений. Даже удалённый позднее КМ
остаётся в снимке и диагностике обращения. Действия фиксируются начиная с этого
обновления; отдельного общего журнала в интерфейсе нет. Индивидуальные аккаунты
сотрудников не вводятся: действия различаются по роли «Склад»/«Администратор».

Администратор вводит результат разбора и нажимает **«Закрыть обращение»**.
Успешная повторная проверка сама не снимает подсветку: ответственному нужно увидеть
и закрыть обращение. Закрытие обращения не меняет состав и не заменяет проверку КМ.
Обращения и их снимки доступны также для документов в корзине.

В общем списке КМ появился поиск по коду/GTIN и флажок **«Только ошибки»**.
Нажатие на GTIN в таблице раскрывает связанные сканы. Фильтрация ничего не удаляет,
не пересчитывает количества и не обращается к ГИС МТ. Ошибки показываются по последней
проверке; при изменении состава сохраняется пометка о неактуальности результата.

Новые таблицы SQLite: `warehouse_issues` (снимки и разбор обращений), `warehouse_events`
(действия для диагностики документа). Они создаются автоматически в текущей базе.
В них не сохраняются административные ключи и токены. Резервная копия общей SQLite
включает и эти данные.

Дополнительные API:

- `GET /api/warehouse/documents`: `org_inn`, `scan_state=all|unscanned|scanned`, `kind`, `status`.
- `GET /api/admin/warehouse/documents`: те же фильтры плюс `query`, `date_from`, `date_to`,
  `issue_state=all|open|closed|none`, `trash=true|false`.
- `POST /api/warehouse/documents/{id}/issues`: JSON `version`, `result_at`, необязательный `message`.
- `POST /api/admin/warehouse/documents/{id}/restore`: JSON `version`, `revision` из карточки корзины.
- `GET /api/admin/warehouse/documents/{id}`: администратор может прочитать также документ корзины.
- `GET /api/admin/warehouse/documents/{id}/issues`: список обращений.
- `GET /api/admin/warehouse/documents/{id}/issues/{issue_id}`: сохранённый снимок обращения.
- `GET /api/admin/warehouse/documents/{id}/issues/{issue_id}/events?before=<id>`:
  действия по документу, по 100 записей, `next_before` для следующей страницы.
- `POST /api/admin/warehouse/documents/{id}/issues/{issue_id}/resolve`: JSON `resolution`.

Справочный расчёт количества по прошлым приёмкам в это обновление не включён:
локальные сведения могут быть неполными или устареть после разделения КМ. До явной
проверки фактическая таблица по-прежнему не рассчитывается.

### Возврат ответа на склад

В разборе обращения администратор может выбрать **«Вернуть на склад»** и написать
обязательный комментарий: что исправлено и что нужно сделать сотрудникам.
Открытое обращение при этом закрывается, а ответ сохраняется отдельно до прочтения.
Кнопка доступна для документа в работе. Завершённый документ нужно сначала явно
возобновить; возврат ответа сам не запускает и не переоткрывает операции.
Можно передать комментарий также по уже закрытому обращению.

На складе документ с непрочитанным ответом поднимается выше обычных и получает пометку
**«Ответственный ответил — можно продолжать»**. Внутри видны текст и дата ответа.
Кнопка **«Продолжить работу»** подтверждает прочтение; это общее подтверждение по документу,
которое синхронизируется на всех устройствах. Оно не запускает проверку и не меняет состав.

Сканирование, проверка и завершение по актуальному успешному результату доступны и до
подтверждения ответа. Количество товара по-прежнему меняется только после явной проверки.
Ответ, подтверждение прочтения и даты сохраняются после перезапуска backend и видны
в истории обращения. Повторная отправка с тем же `request_id` или повторное подтверждение
с другого устройства не создают дубли. Для этих данных автоматически создаётся таблица
`warehouse_returns` в общей SQLite.

API:

- `POST /api/admin/warehouse/documents/{id}/issues/{issue_id}/return`:
  JSON `resolution` (комментарий), `request_id` (идентификатор повторяемого запроса).
  Нужен административный доступ и стандартная защита записи с cookie.
- `POST /api/warehouse/documents/{id}/returns/{reply_id}/acknowledge`:
  склад подтверждает прочтение ответа. Ответ другого документа подтвердить нельзя.
- `GET /api/warehouse/documents/{id}` возвращает `warehouse_replies` и `pending_returns`;
  список документов включает число непрочитанных ответов. История ответов с датами
  прочтения также доступна в административной карточке обращения (`returns`).

### Единый интерфейс

Сверка, склад и админка используют общую навигацию и настройку темы `gis_theme`.
Светлая/тёмная тема сохраняется при переходах и синхронизируется между вкладками одного
браузера. В складских экранах унифицированы карточки, поля, кнопки, статусы и диалоги;
реквизиты и редактирование плана вынесены в раскрываемую секцию. Появились подписи
полей PN и количества, индикация выполнения действий и компактный мобильный экран.
На складе основной блок сканирования расположен перед таблицей; «Ручной ввод» включает
экранную клавиатуру, «Режим сканера» возвращает аппаратный ввод без её вызова.

Браузерный тест дополнительно проверяет возврат/прочтение на независимых клиентах,
сохранение возможности сканировать, тему после перехода в существующую сверку,
ручной ввод и отсутствие горизонтального переполнения мобильной страницы.
Для визуальной проверки можно сохранить его скриншоты:
`WAREHOUSE_SCREENSHOTS=/tmp/warehouse-ui python tests/browser_warehouse.py`.


### Настройки приложения

В админке появился четвёртый раздел **«Настройки»** (`/admin?section=settings`).
Параметры сохраняются в общей SQLite и действуют на всех устройствах без перезапуска.
Исходные значения указаны в форме настроек.

- **Функции:** обращения склада, возврат с комментарием, удаление сканов складом,
  кнопка ручного ввода, автоматическое получение PN из True API, обязательный комментарий обращения.
- **Документы:** строгое соответствие организации для новых отгрузок, организация приёмки
  по умолчанию, допустимые статусы отгрузки (`EMITTED`, `APPLIED`, `INTRODUCED`),
  ожидание проверки документа от 30 до 540 секунд.
- **Отсутствующие КМ при приёмке:** список в документе и обращении показывается,
  только если количество отсутствующих КМ строго меньше заданного порога
  (по умолчанию 20, диапазон 0–10000). При равенстве и превышении видно только
  общее количество; 0 всегда скрывает список. Настройка меняет отображение,
  полный результат проверки и возможность завершения документа сохраняются.
  Незаполненная приёмка без ошибок в считанных КМ показана жёлтым с предложением
  продолжить сканирование. Ошибки в считанных кодах показаны красным.
- **Повторный скан:** «ОК, продолжить» сохраняет исходный КМ в документе;
  «Удалить код из документа» удаляет его на сервере и на всех устройствах.
  Очередь следующих сканов ожидает решения сотрудника. Удаление доступно,
  если включена настройка удаления сканов складом.
- **Вердикты сверки:** «Допустимо», «Внимание», «Ошибка» для трёх известных статусов;
  для неизвестного статуса доступны «Внимание» и «Ошибка». Эти вердикты применяются
  к одиночной и пакетной сверке отдельно от правил отгрузки.

Кнопка «Исходные настройки» только заполняет форму: для применения нужно сохранить.
«Загрузить текущие» отменяет черновик после подтверждения. При конфликте двух
администраторов сохранение возвращает 409 и сохраняет черновик в открытой форме.
История показывает последние 50 изменений с датами и значениями до/после.

Изменение допустимых статусов делает результаты всех незавершённых отгрузок
(включая корзину) неактуальными. Завершение доступно после новой успешной проверки.
Результат проверки, начатой до изменения правил, также не разрешает завершить документ.
Состав и сканы сохраняются; завершённые документы и проверки приёмки не изменяются.
Строгость владельца по умолчанию влияет только на новые документы. Остальные параметры
проверки берутся на момент её запуска. Выключение обращений/возврата/удаления сканов
проверяется сервером, сканирование остаётся доступным. Уже переданные ответы можно прочитать.
Ручной ввод управляет кнопкой экранной клавиатуры, а не определяет источник ввода.

Обязательные проверки структуры КМ, ошибок API, владельца, достоверного количества,
соответствия составу и криптографической части сохраняются. Приёмка остаётся точной
локальной сверкой с исходным документом.

API: защищённый `GET /api/admin/warehouse/settings` возвращает `runtime` (`revision`,
`updated_at`, `values`), `defaults`, `schema`, `history` и существующий справочник.
`PUT /api/admin/warehouse/settings` принимает `{revision, values}`. Запись требует
административного доступа и стандартной защиты cookie-запросов. Неизвестные поля,
неверные типы и недопустимые значения отклоняются. Таблицы `application_settings`
и `application_settings_history` создаются автоматически; новые зависимости не нужны.
`RECEIPT_DEFAULT_ORG` служит исходным значением до первого сохранения настроек.
