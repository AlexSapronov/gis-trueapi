# Связь marking-bm → gis-trueapi: приёмка по накладной

После успешного формирования всех АТК группы поставщика marking-bm сохраняет в своей SQLite-базе состав **каждой накладной отдельно**. Фоновая передача создаёт в gis-trueapi один черновик приёмки на накладную. Несколько АТК одной накладной объединяются в этот черновик; несколько накладных внутри одного АТК остаются отдельными заданиями. Склад увидит документ только после ручного запуска администратором.

Передаются полный исходный КМ с крипточастью (без изменения регистра), PN, количество товара в каждой упаковке, номера АТК, поставщик, номер накладной и ИНН нашей организации. Дата приёмки первоначально берётся из даты создания накладной в marking-bm: отдельного поля даты накладной там сейчас нет.

## Настройка на одном VPS

1. Сделайте согласованные backup обеих баз штатными средствами приложений.
2. Обновите сначала gis-trueapi, затем marking-bm из соответствующих PR после их слияния. Новые таблицы создаются автоматически, существующие документы и сканы не меняются.
3. Один раз сгенерируйте отдельный ключ на сервере:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

4. В конфигурацию gis-trueapi (его .env либо EnvironmentFile systemd) добавьте:

```dotenv
RECEIPT_BRIDGE_KEY=<сгенерированный ключ>
```

5. В /etc/marking-bm.env добавьте тот же ключ и локальный адрес gis-trueapi:

```dotenv
BM_RECEIPT_BRIDGE_URL=http://127.0.0.1:8000
BM_RECEIPT_BRIDGE_KEY=<тот же ключ>
```

Порт 8000 указан по текущему README gis-trueapi. Если реальная служба слушает другой порт, замените его. Адрес задаётся без пути /api. HTTP разрешён только для loopback; для удалённого подключения нужен HTTPS. Новый сетевой порт не нужен. Ключ не должен совпадать с ADMIN_KEY, паролем администратора или токеном подписанта.

6. Проверьте, что ИНН в настройках организации marking-bm присутствует в ORGANIZATIONS gis-trueapi. Получатель приёмки определяется именно по этому ИНН.
7. Перезапустите службы:

```bash
sudo systemctl restart gis-trueapi.service
sudo systemctl restart marking-bm.service
sudo systemctl status gis-trueapi.service marking-bm.service --no-pager
```

## Проверка работы

После формирования следующего комплекта АТК:
- В marking-bm: «Администрирование → Подключения и подпись → Задания на приёмку» — строка по каждой накладной и статус «Передано в приёмку».
- В gis-trueapi: админка → приёмка — черновик с тем же номером, PN, КМ и количеством; в карточке указаны поставщик и АТК.
- До нажатия «Запустить» задание не видно складу.
- После запуска склад сканирует и сверяет точный состав обычным способом.

Очередь не расходует платные КМ и не создаёт новых операций в ЧЗ. Она включается отдельными настройками подключения, независимо от BM_ALLOW_EXTERNAL_WRITES. Подпись ЭЦП для передачи задания не требуется.

## Повторы и изменения

Идентичность задания: постоянный ID установки marking-bm + внутренний ID накладной. Одинаковые номера разных накладных не объединяются. Повтор после потери ответа возвращает тот же документ. Версии монотонны; устаревшая версия и другой состав с тем же номером версии отвергаются.

До запуска новый подтверждённый состав АТК обновляет связанный черновик. После запуска/завершения изменения блокируются (HTTP 409), сканы и состав приёмки сохраняются. Ошибка видна в marking-bm; автоматического сброса приёмки или удаления сканов нет. Для таких случаев требуется отдельный разбор администратором. Удалённая/архивная приёмка также не пересоздаётся.

При потере связи состав остаётся в SQLite и повторяется через 1, 2, 4, 8, 16, затем до 30 минут. Одна передача за проход worker ограничивает задержку основной очереди; остановленные документы/группы не передаются. Подтверждение старой версии не может пометить новую версию переданной.

Первоначально передаются комплекты АТК, сформированные или переформированные после обновления. Автоматической массовой загрузки старых АТК нет. Восстановление backup сохраняет идентификатор установки и очередь: не запускайте две копии одной восстановленной базы одновременно.

## API и ограничения

POST /api/integrations/marking-bm/receipts — отдельный ключ в X-Receipt-Bridge-Key; административный ключ и cookie не заменяют его. Ключ не открывает сканирование, токены ЧЗ или административные операции.

До 50 000 КМ и 32 МиБ на запрос. Используются существующие правила приёмки: один GTIN соответствует одному PN, GTIN проверяется, полный КМ с крипточастью обязателен. Количество хранится явно, а не извлекается из AI 30 скана. Ошибки формата не возвращают сырые КМ в ответе.

Проверки: python -m pytest -q tests/test_receipt_bridge.py в каждом репозитории.
