# Связь marking-bm → gis-trueapi: приёмка по накладной

Редакция: 16.11.2026. Документ одинаков в обоих репозиториях.

## Назначение

После формирования всех АТК группы поставщика marking-bm сохраняет состав каждой накладной отдельно. Фоновая передача создаёт один черновик приёмки на накладную; склад видит его только после ручного запуска администратором gis-trueapi. Несколько АТК одной накладной объединяются в один черновик; несколько накладных внутри общего АТК остаются отдельными заданиями.

Передаются полные КМ с крипточастью и регистром, PN, количество в упаковке, номера АТК, поставщик, номер накладной и ИНН организации. Дата приёмки первоначально берётся из даты создания накладной в marking-bm, поскольку отдельного поля даты накладной там нет.

## Настройка

1. Сохраните согласованные резервные копии обеих баз. Обновите сначала gis-trueapi с поддержкой отзыва, затем marking-bm.
2. Сгенерируйте отдельный случайный ключ: `python3 -c "import secrets; print(secrets.token_urlsafe(48))"`.
3. В защищённой конфигурации gis-trueapi задайте `RECEIPT_BRIDGE_KEY`.
4. В `/etc/marking-bm.env` задайте тот же ключ как `BM_RECEIPT_BRIDGE_KEY` и адрес получателя:

```dotenv
BM_RECEIPT_BRIDGE_URL=http://127.0.0.1:8000
BM_RECEIPT_BRIDGE_KEY=<сгенерированный ключ>
```

HTTP допустим только для loopback. Для другого сервера требуется HTTPS. Порт 8000 — пример, замените на порт своей установки; адрес задаётся без `/api`. Ключ отличается от ADMIN_KEY, пароля администратора и токена подписанта. ИНН организации marking-bm должен присутствовать в ORGANIZATIONS gis-trueapi.

5. Перезапустите обе службы и проверьте их состояния:

```bash
sudo systemctl restart gis-trueapi.service
sudo systemctl restart marking-bm.service
sudo systemctl status gis-trueapi.service marking-bm.service --no-pager
```

## Доставка, повторы и ручной разбор

Идентичность задания — постоянный ID установки marking-bm + внутренний ID накладной. Повтор после потери ответа не создаёт дубль. Версии монотонны; устаревший состав и другой состав с тем же номером версии отклоняются.

До запуска новый состав обновляет связанный черновик. Обычная доставка сама по себе не сбрасывает начатую/завершённую приёмку: конфликт требует разбора либо отдельного сценария отзыва. Неизменный повтор связанного архивного документа подтверждается без изменения его данных.

При потере связи очередь сохраняется в SQLite и повторяет доставку с увеличивающейся задержкой до 30 минут. Остановленные документы и группы не передаются. Подтверждение старой версии не отмечает новую версию доставленной. Передача не требует УКЭП, не расходует КМ и включается независимо от BM_ALLOW_EXTERNAL_WRITES.

В marking-bm проверьте «Задания на приёмку»: номер накладной, версию, статус и ошибку. В gis-trueapi проверьте черновик, организацию, PN, КМ и количество, затем явно запустите приёмку. Кнопка «Повторить передачу / отзыв» в marking-bm повторяет ту же версию без нового заказа КМ и расформирования.

## Историческая догрузка

После включения связи worker небольшими порциями находит ранее готовые накладные без передачи. Он проверяет актуальные АТК и КМ в ЧЗ: уже введённые в оборот пропускаются, ошибки сохраняются для повтора. Начатый ввод, остановленные документы и незавершённые АТК не догружаются.

gis-trueapi ищет существующую приёмку по ИНН/номеру и пересечению КМ. Единственное полное совпадение КМ, крипточасти, PN и количества связывается без изменения статуса, сканов, даты и проверок, включая завершённый или архивный документ. Полное совпадение КМ позволяет найти приёмку с другим номером. При отсутствии совпадений создаётся черновик. Несколько кандидатов, частичный состав, другое количество/PN/крипточасть/организация, корзина или чужая связь дают конфликт.

## Отзыв при исправлении готового груза

marking-bm — источник истины для версионного состава. При административном исправлении груза он сначала отправляет отзыв прежних приёмок, затем после подтверждения отзыва разрешает подпись/отправку расформирования АТК. Недоступное соединение повторяется из очереди.

Отзыв имеет приоритет над любым статусом приёмки, включая активную проверку, завершение, архив и корзину. Старые строки, сканы и проверки сохраняются в истории; текущие сканы и результат сбрасываются. Отозванная версия убирается из работы. Отзыв идемпотентен и сохраняется, даже если первоначальная доставка ещё не пришла. Старые/повторные доставки не восстанавливают отозванный состав.

После новых АТК передаётся более высокая версия и открывается новый черновик. Запоздавшая проверка не возвращает старый результат. Это отдельный контролируемый сценарий; обычная повторная доставка не равнозначна отзыву.

## API и ограничения

| Метод и путь | Назначение |
|---|---|
| `POST /api/integrations/marking-bm/receipts` | Доставка состава приёмки |
| `POST /api/integrations/marking-bm/receipts/revoke` | Отзыв с source_instance, source_document, возрастающим revision, action=revoke и reason |

Оба маршрута требуют `X-Receipt-Bridge-Key`. Административная cookie и X-Admin-Key его не заменяют. Ключ не открывает токены ЧЗ, складское сканирование и административные операции.

Доставка ограничена 50 000 КМ и 32 МиБ. Один GTIN соответствует одному PN, GTIN проходит проверку, полный КМ с крипточастью обязателен. Количество передаётся явно и не извлекается из AI 30 скана.

Проверка: `python -m pytest -q tests/test_receipt_bridge.py` в каждом репозитории. При восстановлении backup сохраняются ID установки и очередь; нельзя одновременно запускать две копии одной восстановленной базы.
